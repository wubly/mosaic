# Decisions

One line per decision: `Mn: decision`.

- M0: Commit attribution uses `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` (the model actually running), not the Opus 5.5 line in the spec.
- M0: Material Symbols Rounded variable TTF is 15 MB; kept whole for now, subsetting deferred to packaging.
- M2: Local scanner cache uses its own `{v, entries}` layout (version 1) and never deletes the cover dir on a version change, so migrated covers survive.
- M2: Local track sorting uses a case/accent-insensitive key (NFKD, lowercase) instead of JS `localeCompare`.
- M2: Spotify/YouTube-free `Services` takes a shared `Arc<Mutex<Config>>`; the app mutates it via `Services::update_config`, which persists.
- M2: Embedded lyrics: SYLT (ms timestamps) parsed via lofty's MpegFile; other lyrics frames and `LYRICS` comments via lofty `ItemKey::{Lyrics,UnsyncLyrics}`.
- M3: Engine uses symphonia 0.6 / rubato 5 / cpal 0.18 (current releases); gapless trimming comes from symphonia's `AudioDecoderOptions::gapless` (default on) since `FormatOptions` no longer has `enable_gapless`.
- M3: Deck rings persist for the engine's lifetime; each Load spawns a decoder thread that pushes a Flush marker (epoch, source position) so the callback discards stale audio. EOF is signalled via `DeckShared::eof_frame` instead of a marker.
- M3: The cpal stream is created and owned inside the control thread (cpal streams are not `Send` on all platforms). `SourceSpec` currently has only `File`; `Http`/`Hls` land in M4 and `Push` in M11. `SetEq`/`SetLeveling`/`SetSpeed` are accepted but wired up in M4.
- M4: HTTP and HLS sources use blocking `ureq` on the decoder thread (no tokio dependency in `audio`); progressive seeks restart the download with a `Range` request when the target is beyond the buffered window, and a response without `Content-Length` is treated as non-seekable.
- M4: A 403/410 from a stream or HLS segment surfaces as `Error { message: "stream expired" }` so the controller can re-resolve once.
- M4: The compressor has no makeup gain (WebAudio adds some).
- M4: Network source tests use a raw `TcpListener` server because tiny_http chunk-encodes bodies over 32 KB and so hides `Content-Length`.
- M5: Auto steps (end of track, tail skip) load the next track on the other deck and unload the old one; manual steps reuse the active deck. True pre-loaded gapless at crossfade 0 is not done yet (the next load starts at `Ended`).
- M5: Repeat-one after EOF reloads the track (the decoder has exited, so a seek can't restart it); from tail-skip it seeks. End-of-track sleep triggered by a tail skip pauses the deck (the JS let the track run on and then advanced).
- M5: A play is recorded 20 s after each `load`, not after a session restore (the JS recorded a play for a restored track that was never played).
- M5: Pause/sleep fades are per-deck gain; the follow-up "restore volume" is a gain reset to 1 sent on the `Paused` event, because master volume is a separate engine parameter.
- M5: `core::queue::step_index` is the free-function form of `next_index_with` so the controller can walk past unavailable tracks.
- M5: `app/src/main.rs` carries a temporary `allow(dead_code)` on `mod player`; remove it in M7 when the UI consumes every effect.
- M6: Icons are two static subsets (`MosaicSymbols-filled/outlined.ttf`, generated by `assets/fonts/make-icons.py` from the variable font) because iced can't set font axes; the 15 MB variable TTF is no longer tracked or embedded (this resolves the M0 subsetting note).
- M6: Dynamic theme uses `material_colors::palette::CorePalette` (deprecated, but it is what `themeFromSourceColor` builds on, so tones match the JS) and animates with CSS `ease` over 900 ms in linear sRGB.
- M6: Widget styles take a `Palette` by value (closures capture it); `App::theme()` returns an `iced::Theme::custom` from the current interpolated palette only for built-in widget defaults.
- M6: iced's own tokio runtime runs all `Task`s (no separate 4-worker runtime); `Services` needs no runtime handle.
- M6: `--debug-screenshot <path>` saves the app window (via `window::screenshot`) after 3 s and exits; used for visual checks without capturing the desktop.
- M6: Ambient image is drawn with `Image::scale(1.3)` + Cover instead of `inset: -15%`; the lyrics aside appears without its spring animation until M10.
- M6: Crate-level `allow(dead_code)` in `main.rs` until views consume the style/icon/anim helpers; removed in M13.
- M6: Idle CPU (release build, nothing playing) measured at ~0.5 % of a core.
- M7: Media controls use souvlaki with the `use_zbus` backend (no libdbus); the Windows HWND is passed as `None` for now (SMTC needs it; wire `window::run` + raw-window-handle when building on Windows). MPRIS verified with `playerctl` on Linux.
- M7: Discord status exposes `enabled/connected/error` only (the IPC crate doesn't return the Discord username). Timestamps are anchored at push time (position + time since the update) rather than at update time, so a throttled push doesn't drift.
- M7: Seek bar position is extrapolated between the engine's 100 ms Position events while playing; frames run only while a track is playing/loading.
- M7: Player-bar entrance spring, thumb swap animation and the play-icon scale/rotate swap are omitted; the play button radius spring (420/28), wave amplitude tween and spinner are implemented.
- M7: Tune popover is positioned at a fixed offset above the right tools cluster instead of anchoring to the button; it dismisses on Esc or a click outside.
- M7: Not verified here: Discord "Listening to" display (no Discord running) and GNOME/KDE widget cover rendering; MPRIS metadata/status/next verified via playerctl.
- M8: Track clicks carry a `TrackRef { list: ListRef, index }` instead of a cloned list; `App::resolve_list` rebuilds the list when the click is handled (results are re-filtered with `filter_along` like `queueable`).
- M8: Context menu opens at the last known cursor position (tracked from `CursorMoved`), so "more" buttons open it at the button and right-click at the pointer; it is clamped using an estimated height.
- M8: Skeletons are static blocks (no shimmer); search-bar focus animation and the tile hover lift/entrance animation are omitted. Tiles use a wrapping row (fixed 156/148 px) rather than a stretching CSS grid.
- M8: Spotify and YouTube sections of Discover are omitted (YouTube dropped; Spotify arrives in M11). Device hits and the palette's track search use the scanner results held in `App::local`.
- M8: Palette keyboard handling: Up/Down/Esc in the global key handler, Enter via the text input's submit.
- M9: Virtual list = scrollable with `on_scroll` offset + two spacers around the visible rows (fixed 54 px rows, 8 rows overscan); each page passes an estimated list-top offset, the overscan absorbs the error. Verified by unit tests only; the 20k-row 60 fps check was not run.
- M9: Drag reorder uses a grip: press, then the row follows the cursor in whole-row steps (delta from the press point), previewing the new order, and the list is committed on release. The spec's 150 ms press-and-hold is not used (the grip makes it unnecessary).
- M9: Local sorting uses an NFKD/accent/case-insensitive key (no numeric-aware compare); group headers compare the exact artist/folder string like the JS.
- M9: Stats bars animate with the 140/20 spring from 0 on tab entry; the history "when" label is drawn over the row at right:150.
- M9: File dialogs use rfd 0.18 (xdg-portal + wayland, no GTK); drops are batched over 80 ms so several files give one toast and one scan.
- M9: The Spotify import dialog is a placeholder flag (`importing`) until M11; the "Import from Spotify" buttons set it.
- M9: `--debug-view <view>` selects the initial view for screenshots.
- M10: The word-fill lyrics are built from stock widgets (a dim label plus a bright copy in a `clip(true)` container of width `p × word_width`) instead of a custom `advanced::Widget`; word widths and wrapped line counts come from `iced::advanced` paragraph measurement (`text_measure.rs`) so the scroll target can be computed without layout feedback.
- M10: Lyrics line emphasis uses an opacity spring (`lyr-pos`, 170/26) that interpolates 1 / 0.55 / 0.28 / 0.22 by distance; the 0.96 scale and the top/bottom fade mask are omitted. Auto-scroll runs a spring (`lyr-scroll`) and issues `scroll_to` only while it moves, so manual scrolling is free between lines.
- M10: The Now Playing overlay reuses the ambient layer under a 62 % surface fill; the enter/exit slide is omitted. Mini mode resizes the same window to 380×660 (min 340×440, always-on-top), and back to the remembered size (min 980×640).
- M10: The visualizer reads the analyser at ≤30 fps only while Now Playing is open and the music plays or bars are decaying.
- M10: The 1 Hz player tick subscription runs only while something needs it (`PlayerController::wants_tick`), keeping idle CPU near zero.
- M10: Debug builds redraw continuously at high CPU (software-heavy debug wgpu path); idle CPU is judged on the release build (≈1.4 % discover, before gating the tick).
- M10: Not verified here: word-by-word fill against the Electron app on a word-stamped track, `.lrc` sidecar pickup in the UI, persistence of a chosen version across restarts, always-on-top on X11.
- M11: librespot 0.8.0 (core/playback/metadata/oauth) with `default-features = false` and rustls-native-roots TLS (no OpenSSL, no audio backends); `cargo update vergen --precise 9.0.6` is needed because librespot-core's build script breaks with vergen 9.1 (mismatched `vergen-lib`). The `spotify` cargo feature (default on) lives on `mosaic-services` and is forwarded by the app; without it Spotify tracks are "unavailable" and the browsing/import UI stays.
- M11: `services::spotify::playback` doesn't depend on the audio crate: `load` takes a `Target { write, finish, fail }` of closures, which the app builds from `audio::PushProducer`. Pause/resume/stop follow the controller's `playing` flag (`App::sync_spotify`); seeks reach librespot through the push source's `on_seek` callback.
- M11: Playback login uses librespot's own client id and the `http://127.0.0.1:8898/login` redirect through `librespot-oauth`, cached in `<data>/librespot/credentials.json` (audio cache `<cache>/librespot-audio`, 1 GiB). The Web API flow (user's client id, `/callback`) shares port 8898 but never runs at the same time.
- M11: `Effect::ResolveStream` now carries `seek_to`, because librespot needs the start position when the track is loaded; Spotify errors from the engine ("…needs Premium", "…isn't available…") pass through to the player bar.
- M11: Import reads the embed first (≤100 tracks) and uses the paginated API list when connected and longer; the 4-way matching pool and 30 s per-track timeout follow `useSpotifyImport.js`. Verified against the live embed endpoint (a 50-track playlist matched 46/50).
- M11: Not verified: Spotify sign-in and Web API browsing (needs the user's client id), librespot playback through the engine (needs Premium), the 250-track API import. Connect/disconnect and client-id controls arrive with Settings in M12.
- M12: Onboarding keeps the JS five steps (Welcome, Name, Music, Spotify import, Options) and always shows the import step, because the embed import needs no login; the spec's "Spotify only if beta" is not applied. Reset (Settings → Restart onboarding) applies `Config::reset()` and shows onboarding again.
- M12: Tray: `ksni` (blocking, `async-io` runtime to avoid zbus/tokio feature clashes with souvlaki) on Linux, `tray-icon` elsewhere. Close-to-tray only applies when the tray registered; otherwise closing quits and Settings shows "No system tray found, so closing the window quits Mosaic". The window is hidden with `window::Mode::Hidden` and restored with `Windowed` + `gain_focus` + `request_user_attention`. Windows/macOS tray code is compiled only on those targets and not exercised here.
- M12: Single instance uses `interprocess` (abstract namespace where supported, a socket file in `$XDG_RUNTIME_DIR` otherwise); a second launch sends `focus` or `open <path>` lines and exits (measured 3 ms). Files passed on the command line are added as sources and the first track found plays.
- M12: Settings omit the YouTube and Performance sections; the Spotify block has client-id entry, Connect/Disconnect and an "Enable playback (Premium)" button. The update check runs 5 s after launch and every 6 h; a toast announces a newer release once, the Updates card links to it (the JS had no separate banner).
- M12: Packaging files are in `native/packaging/` (desktop file, AppStream, Flatpak manifest, ebuild) and `[package.metadata.packager]` is in `app/Cargo.toml`. `cargo-packager`, `flatpak-builder` and `dpkg-deb` are not installed on this machine, so the AppImage/.deb/Flatpak builds were not run. The CI workflow is added at M13 because it lives outside `native/`.
- M13: Parity pass. Fixed hooks that were missing from earlier milestones: Ctrl+K and palette arrow keys, cursor/file-drop events, the playback frame gate (wave scroll and position smoothing), the 5 s update check and file arguments at launch, Spotify sections in Discover search, "Go to artist/album" menu items, queue click via `PlayIndex`. Removed the crate-level `allow(dead_code)`; clippy is clean without it.
- M13: Added `tracing` logging (stderr + `<cache>/mosaic.log`, rotated at 5 MB, `MOSAIC_LOG` filter), the one-time "Imported your library from the previous version" toast, a persistent "No audio output device found" banner, `--reset-window` (restores default panel sizes; the app does not persist window geometry), and `.github/workflows/native.yml`, `MIGRATION.md` and the root README rewrite.
- M13: Parity checklist, native vs Electron. Done and exercised in this session (tests and/or screenshots): onboarding steps, greeting, SoundCloud search/charts/related, autoplay and radio (controller tests), local library/sorting/virtual list/drop, queue ops, shuffle/repeat/prev, crossfade/fade/skip silence (controller tests + engine tests), EQ/leveling/speed/sleep, likes/playlists/history/stats, Spotify embed import with SoundCloud matching (live), lyrics (live lrclib) and picker, Now Playing, mini player, dynamic theme + ambient, command palette, shortcuts, MPRIS (playerctl), tray/single instance (single instance exercised), update checker, session restore, Electron-data migration (unit test with a fixture).
- M13: Not verified on a real account/device (code and unit tests only): Spotify sign-in, Web API browsing, librespot playback; Discord presence display; Windows SMTC (needs the HWND, passed as `None`), macOS Now Playing, Windows/macOS tray; always-on-top mini player; word-fill parity against the Electron app; packaging builds (cargo-packager, flatpak-builder, dpkg not installed); the 20k-row/5k-track performance figures.
- M13: Known differences from the Electron app: no YouTube; no low-memory mode; lyric lines fade instead of blur and do not scale; no lyrics-aside/Now Playing/player-bar enter-exit animations; skeletons are static; text selection is unavailable (iced); true pre-loaded gapless at crossfade 0 is not implemented (the next track loads at the end of the previous one).
- M12/M13 follow-up: installed cargo-packager 0.11.8; `cargo packager --release -f appimage` produces `mosaic_0.5.0_x86_64.AppImage` and it runs (`--version`), `-f deb` produces a .deb. The custom desktop template was dropped from the packager config because it made linuxdeploy look for an `app.mosaic.player` icon the packager doesn't generate. Flatpak was still not built (no flatpak-builder).
- M10 follow-up: `crates/services/tests/lrc_sidecar.rs` scans a folder with a sibling `.lrc` and checks the track gets `lrc_path` and `get_lyrics` returns the sidecar lines (origin `file`).
- Perf follow-up: memory went from 350–450 MB RSS (≈255 MB private dirty, 178 threads at startup) to 255–290 MB (≈95 MB private dirty, ≈41 threads). Causes: unbounded artwork decodes each on its own blocking thread (now 4 at a time, big covers box-sampled before Lanczos), iced's default tokio runtime (now a custom `Executor` with 2–4 workers and 12 blocking threads), glibc per-thread arenas (`mallopt` arena max 4, fixed 256 KB mmap threshold), and wgpu bringing up EGL/GL and Mesa LLVM next to Vulkan (now `WGPU_BACKEND=vulkan` when a non-CPU Vulkan device can present). Playback-long motion is capped at 60 fps; at a 360 Hz display every vsync rebuilt the whole window (≈10 % CPU while playing). The ~40 MB of system fonts that cosmic-text maps at startup is left, as it would need an iced patch.
- YouTube: playback resolves a video through InnerTube `/player` with the VISIONOS client profile (plain URLs, no player script, no sign-in) and hands the URL to the existing HTTP source; GStreamer is not used because the engine is symphonia/cpal. Opus/WebM is preferred over AAC/MP4: the engine seeks WebM over HTTP, but fails on YouTube's fragmented MP4 (checked against live URLs), so MP4 is only the fallback.
- YouTube: `/player` is sent with an anonymous `visitorData` from InnerTube's `visitor_id` endpoint (cached per run, refreshed once and retried if YouTube still answers "confirm you're not a bot"). Without it only a few very popular videos resolve; the first live test used one of those and looked fine, which is why this was found late.
- YouTube: nothing is cached; every resolve fetches a fresh URL. The player already re-resolves once at the current position on a 403/410 ("stream expired"), and a cached URL would hand back the dead one.
- YouTube: not done yet: the WEB_REMIX playback fallback (player-script solver, proof of origin, pre-roll retry) and SABR streaming.
- YouTube: sign-in is the old Google PKCE flow with the user's own OAuth client (port 8899, `youtube.readonly`); the liked videos and playlists tab uses Data API v3 as in the Electron app. Everything is behind Beta features like Spotify, but playback and search need no account.
- YouTube search is YouTube Music's song search (InnerTube WEB_REMIX `/search` with the songs-only filter), so results have real artist and album names and square art. It is the same signed in or out and never touches the Data API quota; if the music endpoint errors it falls back to the website's video search (WEB client `/search`, videos-only filter; the VISIONOS client returns no video results there). Both client versions are pinned and only need bumping if search starts failing.
- Discover search runs one service at a time, chosen from a dropdown (SoundCloud, Spotify when connected, YouTube with the beta on, This device). The old interleaved SoundCloud+Spotify search and the separate "On your device" block are gone; the pick is kept in memory only and falls back to SoundCloud when its service goes away.
- Not verified: Google sign-in and Data API browsing/search (needs a Google OAuth client; the signed-out search and resolve were run live), audio actually coming out of the speakers for a YouTube track in the running app (the stream was decoded and seeked through the engine's HTTP source in a probe, and the resolve path was run via `--debug-cmd yt-stream`).
- YouTube similar tracks: autoplay at the end of the queue and "Start radio" work from YouTube tracks via YouTube Music's radio (`/next` with the `RDAMVM<videoId>` playlist, up to 50 tracks, seed removed), same as SoundCloud's related list. The relevance filter only applies to SoundCloud candidates, so it passes these through.
- Engine HTTP source: every request now carries `Range: bytes=N-`, including the first from 0. YouTube serves an unranged GET at ~30 KB/s (slower than playback), which stalled the engine until its 20 s body timeout fired around 40 s in ("Playback failed"). It was throttling, not an ad; servers that ignore Range still answer 200 and are handled as before.
- Engine errors are now logged (`engine error: …` at warn level), since the player bar only ever says "Playback failed".
- 0.6.2 Spotify: on Windows and macOS, Spotify plays through Spotify's Web Playback SDK in the system web view (WebView2 / WKWebView via wry 0.57 + tao 0.37), not librespot or Soloist. Research and measurements: `../docs/spotify-cef-backend.md`. Stock CEF was rejected (no AAC, which is the only format the SDK streams to software DRM); installed Chrome and Firefox-family browsers were tested as the Linux engine but not adopted yet, so Linux keeps librespot/Soloist.
- 0.6.2 Spotify: the web view runs in a separate process, `mosaic --spotify-host` (same executable, so installers need nothing new), because WebView2/WKWebView want their own main-thread event loop next to iced. Its config (the page URL with the bridge secret) goes over stdin, never argv; closing stdin ends it, and Mosaic also kills it on exit (`kill_on_drop`).
- 0.6.2 Spotify: the page talks to Mosaic over a loopback bridge (`web/bridge.rs`): random port, Origin check, a per-run secret in the URL fragment and a `hello` handshake. Mosaic starts each track with Web API `PUT /me/player/play?device_id=…` with exactly one URI (Mosaic keeps its own queue) and drives pause/seek/volume through the SDK.
- 0.6.2 Spotify: the tracker (`web/tracker.rs`) follows measured SDK behaviour: the page extrapolates `position` from `timestamp` (the SDK's position is a snapshot); a requested URI may come back relinked (`linked_from`); a finished single-URI play is `paused` at 0 on the same track; another track after ours means Spotify moved on (Mosaic finishes and pauses Spotify). Like Soloist, the deck gets silence paced by Spotify's clock; the feeder is a copy of Soloist's rather than a shared module, to leave Soloist untouched.
- 0.6.2 Spotify: WebView2 runs with trimmed switches (`spotify_host.rs`, 184 MB private / 7 processes while playing, 179 MB measured in-app). The host stops after 10 minutes without a Spotify track. wry/tao are pinned below 0.58/0.38 because those move Linux to GTK 0.19, which clashes with tray-icon's GTK 0.18 in the lockfile even though wry is only built on Windows and macOS.
- 0.6.2 Spotify: the PKCE scopes gained `streaming user-read-playback-state user-modify-playback-state`; older sign-ins get "Reconnect Spotify in Settings → Beta". Soloist settings are only shown on Linux.
- 0.6.2 Not verified: macOS (WKWebView with FairPlay) at all; the Settings section and reconnect flow in the running UI; pause/seek/volume from the UI (the SDK operations were measured in the spikes, and the app path was run with `--debug-cmd sp-play`: start, natural end, next track, queue end); the 10-minute idle shutdown.
- 0.7.0: Catalog search (`services::catalog`): YouTube Music uses the WEB_REMIX artist/album/featured-playlist search filters and `browse` pages; SoundCloud users stand in for artists and sets for albums/playlists (bare set tracks are looked up through `/tracks?ids=`, 50 at a time); Monochrome has artists and releases only, since its public API has no playlist lookup. Spotify keeps its own pages (follow/save), but its search hits are shown as the same cards.
- 0.7.0: Label releases on SoundCloud are usually Go+ previews, so their album pages can be empty; the page says so instead of failing.
- 0.7.0: The YouTube tab reads the signed-in account from the cookie session only (history, home, likes, playlists, artists, all at once), prefetched at start and right after sign-in, like AsterTune; the developer-client library is kept only for whoever has no Google sign-in.
- 0.7.0: Google sign-in opens the user's own browser on a Mosaic-only profile (embedded web views are refused by Google, and Linux has none): Chromium-family browsers through the DevTools protocol, Firefox-family through WebDriver BiDi. Google still refused a browser under remote control (hiding `navigator.webdriver` was not enough), so the sign-in is two steps: a plain window with no remote protocol, which Mosaic closes itself once YouTube Music shows (read from the tabs the browser saves: Firefox's `recovery.jsonlz4`, decoded in-tree, with the save interval set to 1 s; for Chromium the literal `https://music.youtube.com/` in the newest `Sessions/Session_*` file), or which the user closes; then the same profile opened headless with the protocol on, only to read the cookies. Chromium runs with `--password-store=basic` both times so the headless run can decrypt what the window stored. The profile keeps its Google session, so signing in again later is one click. Flatpak browsers get their profile in `~/.var/app/<id>/data`, and since a Flatpak outlives `flatpak run`, leftover processes on that exact profile path are stopped. The web view window remains the fallback on Windows/macOS without a browser. `VISITOR_DATA` and `DATASYNC_ID` are read from the page and sent as the visitor id and `onBehalfOfUser`.
- 0.7.0: Autoplay tracks which track its fetch is for; a track played while another's fetch is out gets its own fetch at once, and the stale answer is ignored.
- 0.7.0: The debug players (`--debug-cmd queue-play`, `search-play`, …) start at volume 0; `MOSAIC_DEBUG_VOLUME` sets another.
- 0.7.0 Animations: content motion lives in the widget tree (`widgets::appear`), not in `AnimationClock`: cards and tiles rise and grow into place with a short stagger when a list first shows or its first items change (`appear::list_key`); the player bar slides a new track's cover and title in; play/pause and hearts pop when they flip (a heart's pop is grouped by track, so rows reused by the virtual list while scrolling don't pop). Only drawing is transformed (iced has no opacity layer, and the glass panel rules out veils), so layout and clicks never move. Loading placeholders pulse (`widgets::skeleton`, one shared clock, 30 fps). Each widget requests frames only while it moves; idle CPU is unchanged (≈0.2 % of a core). `MOSAIC_SLOW_MOTION=<n>` slows this motion and `MOSAIC_SHOT_AFTER_MS` times `--debug-screenshot`, for checking frames.
- 0.7.0 Memory: artwork is decoded at the window's real scale factor (it was always 2×, so 4× the pixels on a 1× screen), handles nothing has drawn for 60 s are dropped (what the latest frame showed always stays) along with the services' decoded-image LRU, and freed heap goes back with `malloc_trim`. Measured on this machine (1× display, NVIDIA): anonymous memory 42→36 MB idle on Home, 49→37 MB after a SoundCloud search, 44→41 MB after a YouTube search. The ~80 MB of NVIDIA driver mappings and ~32 MB of the binary's own pages make up most of the remaining RSS; the GL backend maps ~35 MB less driver than Vulkan here but was left alone (see the Vulkan choice above).
- 0.7.0 Search: no Search sub-tab; every service page has the service's search bar in its header strip (next to Library/Account where there are tabs), and typing shows that service's results in place of the page, clearing it brings the page back (Esc steps back out of an opened artist/album page, then out of the search). What was typed carries over when switching services. `/` and the palette search where you are on a service page, else on Home.
- 0.7.0 Search order: `services::catalog::section_order` puts the section the query names first: an exact artist name → artists, "artist + song" or a song's title → songs, an album title or "artist + album" → albums (a single/EP is discounted so its song stays first), "…playlist" → playlists; otherwise songs, artists, albums, playlists. Names compare as lowercase words without accents; a half-typed name counts a little.
- 0.7.0: Go to artist/album works for every service: YouTube rows carry the artist and album pages their subtitle links to, SoundCloud tracks the uploader; the player bar's artist name opens the artist page too.
- 0.7.0: `--data-dir` scopes the single-instance lock to that folder, so a test or second profile runs next to the everyday Mosaic instead of handing its arguments to it.
- 0.7.0 Loudness: every track is measured as it decodes (`audio::dsp::loudness`: BS.1770 K-weighting, 400 ms gated windows) and brought to −14 LUFS, Spotify's and YouTube's default level, so SoundCloud, YouTube and Monochrome match each other and Spotify (which plays outside the engine, normalized by Spotify). Lifts stop at +9 dB and never push the measured peak past −0.5 dBFS; cuts stop at −18 dB. The decoder publishes a gain once it has a second of audio and every half second after; the deck eases toward it quickly for a track's first five seconds (the decoder is only ~0.5 s ahead, so the first estimate is rough) and slowly after, so the level never pumps. It is a setting ("Same volume everywhere", on by default); the engine itself starts with it off so its own tests stay level-exact.
- 0.7.0 Autoplay: YouTube Music's radio is read three pages deep (~150 songs) instead of one, so YouTube fills 50 and Monochrome ~40 (it was 23 and 13). For variety the radio order is shuffled within runs of five, a randomly picked earlier track's radio is blended in as every third song, and songs from the last 150 plays are left out (unless that leaves fewer than ten).
- 0.7.0 Spotify queue: a song played on its own (not from an album or playlist) gives Soloist nothing to line up (`soloist ctl queue` reports an empty queue), so Mosaic's autoplay fills the queue for it from YouTube Music's radio matched on Spotify; with a Spotify album or playlist, Spotify's own queue still leads.
- 0.7.0: the next track's stream (SoundCloud, YouTube) is resolved in the last 30 s of the playing one and used if under five minutes old, so the change of track doesn't wait on the network. Decoding the next track on the idle deck ahead of time is not done.
- 0.7.0 Experimental "Mix services in autoplay": a song the playing track's service doesn't have stays in as its YouTube Music version. Independently, autoplay never queues a song (artist + core title) that is already in the queue from any service.
